# HTTPS pairing contract (v1 secure extension)

UTF-8 JSON, camelCase. QR/pasted JSON: `protocolVersion:1`, `hostId`, `displayName`, `pairingEndpoint` (https://private-IPv4:port, no path/query/credentials), `oneTimeToken` (32 random bytes, lowercase hex), `pairingIdentityFingerprint` (SSH SHA256 fingerprint), `tlsCertificateFingerprint` (SHA256 DER certificate, lowercase hex), `expiresAt` (Unix milliseconds, ten minutes). Pin is obtained ONLY out of band from the PC screen. No network bootstrap endpoint.

TLS uses an ephemeral self-signed certificate with IP SAN. Android checks exact certificate SHA256, validity and HTTPS hostname; redirects prohibited. Pins live only in native process memory. No trust-all verifier and no persistent CA installation. Tokens and request secrets are never logged.

1. POST /v1/requests: existing PairingRequest fields, plus native TLS pin binding before sending. RSA OpenSSH public key only (2048–8192 bits), no options/newlines; secret is 32 random bytes hex. Exactly one request consumes the token. Response requestId (16 random bytes hex), confirmationCode, expiresAt. Code is first unsigned big-endian 32 bits of SHA256(token + exact publicKey + SSH fingerprint), modulo 1,000,000, padded to six digits.
2. PC explicitly approves matching code, device label and public-key fingerprint; only then append public key transactionally. GET /v1/requests/{id}, authenticated by X-PC-Control-Request-Secret, returns pending/registering/verifying/verified/completed/rejected/expired/failed/cancelled. Verifying includes pc (existing PairedPcInfo schema) and 32-byte hex challenge.
3. Android compares scanned SSH host fingerprint against authenticated PC data, then uses existing temporary trust support to authenticate with its Keystore key and execute only hostname.
4. POST .../complete with base64 RSA PKCS1 SHA256 signature of UTF-8 `pc-control-pairing-v1:{requestId}:{challenge}` proves key possession. This proof alone is not independent server evidence of SSH connectivity: the trusted Android client sends it only after SSH succeeds.
5. POST .../finalize commits registration after Android stores connection/trust information. POST .../cancel rolls back uncommitted registration. Both require the request secret. Finalize is idempotent; completed registrations cannot be cancelled. Session expiry/close rolls back only uncommitted changes. Crash recovery is explicit on next launch; conflicting external file edits block restoration.

Limits: one active request, 16 KiB HTTP body, ten-minute expiry, bounded client response/read/connect timeouts, serialized transitions. Server binds only selected private IPv4; firewall Private/LocalSubnet, exact IP/port/executable. No router changes. Normal/error exit and expiry explicitly remove the temporary rule. Forced process termination cannot execute cleanup: stale rules are removed by Recovery or before the next pairing session. The stopped process leaves no listener. Rules use the documented writable PersistentStore; do not assume ActiveStore is a crash-safe dynamic-rule API.

Windows Schannel does not support ephemeral-key certificates for this server path. The per-session PFX is imported into a temporary named user key container (no PersistKeySet), disposed on shutdown; no root trust is installed. Hard-kill cleanup of that OS key container is a deployment test item. See https://learn.microsoft.com/en-us/dotnet/core/extensions/sslstream-troubleshooting#handshake-failed-with-ephemeral-keys.
